# Hermills UI Harness Acceptance Criteria

## 验收原则

实现 Agent 不能自己验收。每次 UI 改动必须由单独 QA/E2E Agent 检查，并提供截图、命令输出或日志证据。

不能只说“完成了”。必须证明用户真的能看清、点到、输入、滚动、理解下一步。

## 视觉验收

- 1366x768、1440x900、1280x720 下页面不能出现内容重叠。
- 不能出现页面级横向滚动。
- 按钮文字必须清楚，包括禁用状态。
- 图标不能压住文字。
- 错误提示不能盖住输入框和主按钮。
- 同类按钮颜色必须一致：主操作蓝色，成功绿色，危险红色，提醒黄色。
- 表单输入文字必须是深色可读，不允许灰到看不见。
- 卡片圆角、边框、阴影必须统一。

## 布局验收

- 每个页面首屏必须能看到标题、说明和主操作。
- 长页面必须在内容区滚动，不能把整个桌面壳挤出屏幕。
- 初始化页面底部按钮必须可达。
- 客户列表和详情面板在 1366x768 下都可用。
- 批量任务页面必须能同时看到任务状态和部分结果。
- 邮箱配置默认页面不能展示 SMTP 主机、SMTP 端口、API token 等高级字段。
- 签名 Logo 页面只能展示文字签名、Logo 上传、预览和保存。

## 文案验收

- 中文模式下，除品牌名、邮箱服务商、API、SMTP、Logo 等必要技术名词外，不出现无意义英文。
- 错误提示必须包含下一步，例如“请检查授权码”或“请复制详情给技术支持”。
- 不允许只显示“本地服务失败”作为最终用户提示。
- 生成中的状态必须告诉用户正在做什么。
- 空状态必须告诉用户下一步点哪里。

## 交互验收

- 所有输入框都能点击、输入、复制、粘贴。
- 单封写信按钮必须在邮箱和官网填写后可点击。
- 批量写信必须逐条返回结果，不等全部完成。
- 失败的批量客户必须显示失败原因，且不阻塞其他客户。
- 邮箱保存后必须自动测试。
- 聊天控制二维码不能出现 `undefined/`。
- 聊天控制未配置公网绑定地址时，必须阻止生成二维码并显示可理解提示。

## 页面专项验收

| 页面 | 必须通过 |
| --- | --- |
| 登录注册 | 注册、验证码、登录、记住状态流程清楚 |
| 初始化 | 每一步都能滚动到底，继续按钮可达 |
| 今日外联 | 统计卡片、今日任务、主操作清楚 |
| 客户管理 | 列表、筛选、详情、邮件预览都可读 |
| 单封写信 | 背调、证据、邮件、评分、修改入口都可见 |
| 批量写信 | 导入、队列、逐条结果、失败原因都可见 |
| 销售资产 | 用户知道这些资料会影响写信质量 |
| 邮箱配置 | 普通用户只填邮箱和授权码即可完成测试 |
| 签名 Logo | 保存后生成邮件自动带签名和 Logo |
| 公司资料 | 保存后能被写信系统用于匹配开发角度 |
| 聊天控制 | 扫码链接真实可用，连接状态明确 |

## 必跑命令

每次 UI Harness 或 UI 改动后至少运行：

```bash
npm run typecheck
npm run test
npm run build
```

如果只改 Harness 文档，可以先运行：

```bash
npm run test -- tests/renderer/ui-harness-docs.test.ts
```

## 必交证据

- 关键页面截图。
- 测试命令输出。
- 构建命令输出。
- 发现的问题清单。
- 已修复的问题清单。
- 未修复但已记录的风险。

## 不合格示例

- “看起来好了”但没有截图。
- “测试通过”但没有命令输出。
- 二维码扫码后打开 `undefined/chat-control/...`。
- 灰色按钮看不清文字。
- 1366x768 下主按钮被挡住。
- 中文页面混入大段英文。
- 邮箱失败只显示“本地服务失败”。
