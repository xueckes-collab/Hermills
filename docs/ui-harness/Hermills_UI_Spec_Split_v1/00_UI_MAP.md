# 00_UI_MAP.md

文档定位：Hermills UI 重做的产品地图。  
适用对象：Codex、Cursor、Claude Code、前端工程师、实现 Agent、验收 Agent。  
读取顺序：先读本文件，再读 `01_VISUAL_SYSTEM.md`、`02_COMPONENT_SPECS.md`、`03_PAGE_SPECS.md`、`04_STATE_SPECS.md`、`05_ACCEPTANCE_CRITERIA.md`。

本文件只回答六件事：Hermills 是什么，用户是谁，核心工作流是什么，技术和项目边界是什么，AI 可以改什么，AI 绝对不能改什么。

---

# 1. 产品定位

Hermills 不是一个普通 AI 工具，不是一个聊天机器人，不是一个开发者控制台，也不是一个传统后台管理系统。Hermills 是一个给外贸销售每天使用的 Windows 桌面外联工作台。

用户打开 Hermills 时，第一感觉应该是：这是一个帮我完成客户开发工作的销售操作台，而不是一个让我学习技术配置、调试模型、看日志、理解 SMTP 或 API 的工程工具。

Hermills 的核心句子是：

输入客户官网和邮箱，Hermills 自动背调客户、匹配公司资料、写出可审核的英文开发信，并帮助用户发送和跟进。

这句话是所有 UI 决策的最高标准。任何页面、按钮、组件、提示、状态、动效，如果不能帮助用户完成这句话里的工作，都应该被删除、隐藏、合并、降级或放进高级设置。

Hermills 的 UI 不是把 AI 能力全部摊开给用户看，而是把复杂的背调、抓取、证据提取、客户判断、开发角度、写信、评分、自动重写、发送、跟进、学习系统，藏在一个清楚、稳定、可信的工作流后面。

---

# 2. 核心用户

Hermills 的主要用户是外贸业务员、外贸老板、小型出口团队、SOHO 外贸从业者、工厂销售负责人。以当前业务背景看，典型用户可能来自地板、室内建材、工程材料、B2B 出口贸易等行业。

这些用户通常不是技术用户。他们不关心模型名、token、Supabase、Hermes Agent、Scrapling、SMTP host、IMAP、API Base URL、日志栈、任务队列、数据库字段、embedding 或向量库。他们关心的是下面这些事情。

他们想快速知道今天要开发哪些客户。他们想输入一个客户官网和邮箱，然后马上得到一封不像群发模板的英文开发信。他们想知道 AI 为什么这样写，最好能看到客户官网上的证据。他们想连接自己的邮箱发出去，但不想理解 SMTP 协议。他们想批量处理客户，但又不希望批量变成黑盒等待。他们想知道哪些客户已经生成、哪些可以发送、哪些失败、哪些需要跟进、哪些已经回复。

因此 UI 的语言必须是业务语言，不是工程语言。技术能力可以存在，但应该放在系统设置、诊断或高级设置里，不应该暴露在每日工作页面中。

---

# 3. 用户成功标准

Hermills UI 成功，不是因为它看起来更花，而是因为用户可以做到下面这些事情。

用户第一次打开软件，能马上知道自己在哪里。用户不需要问“我应该先点哪里”。用户第一次使用初始化流程时，不会被一大堆公司资料字段吓到。用户配邮箱时，不需要懂 SMTP，只需要知道自己要填邮箱授权码或应用专用密码。用户写单封开发信时，只需要输入客户邮箱和客户官网。用户批量写信时，不需要等全部完成才看到结果，而是写好一封显示一封。用户看到邮件草稿时，能看到证据、评分、开发角度和可编辑正文。用户遇到错误时，知道下一步怎么恢复。用户愿意把客户资料、公司资料和邮件草稿放进这个软件，因为界面看起来稳定、专业、可信。

只要某个 UI 决策破坏了这些目标，即使视觉上更炫，也不能通过验收。

# 4. 核心业务流程

Hermills 的最高频流程是单封开发信流程。

用户进入“单封写信”，输入客户邮箱和客户官网。用户点击“分析客户官网并生成开发信”。Hermills 后台执行客户官网抓取、业务证据提取、客户类型判断、公司资料匹配、开发角度选择、英文开发信生成、质量评分和必要的自动重写。用户表面只看到一个清楚的 AI 工作流，不需要手动选择普通抓取、深度抓取、模型、prompt 或工具链。结果出现后，用户看到客户简报、证据来源、推荐开发角度、邮件主题、邮件正文、质量评分和操作按钮。用户可以保存草稿、重新生成、复制、发送开发信或进入客户详情继续跟进。

第二个高频流程是批量开发信流程。

用户进入“批量写信”，上传 Excel、CSV、TXT，或者直接粘贴客户列表。Hermills 解析每一行，按一个邮箱一个客户建立队列。每个客户独立执行背调和写信。写好一个客户，就立刻在结果列表中出现一个可审核结果。失败客户显示失败原因和下一步，不阻塞其他客户。批量流程的 UI 必须像一条外联生产线，用户随时知道谁在排队、谁正在背调、谁正在写信、谁待审核、谁可发送、谁失败。

第三个流程是邮箱配置流程。

用户进入“邮箱”，填写发件邮箱、授权码或 SMTP 密码、显示名称和测试收件箱。系统根据邮箱后缀自动识别 Gmail、Outlook、腾讯、阿里、Zoho 或自定义。用户点击“保存并测试邮箱”。成功时显示“邮箱可用，可以发送开发信”。失败时显示人话原因，例如“邮箱授权失败。请确认你填写的是邮箱授权码，不是登录密码。”高级 SMTP 主机、端口、安全协议、API token、IMAP 参数默认折叠，不出现在普通用户的第一屏。

第四个流程是客户和跟进管理。

用户在“客户”里查看客户列表、邮件状态、质量分、最近更新时间和跟进状态。点击客户后，右侧详情面板显示客户信息、背调摘要、证据来源、开发角度、邮件正文、评分、历史草稿和跟进记录。用户可以重新生成、保存修改、发送、标记状态或查看回复。

第五个流程是聊天控制。

用户选择微信、飞书、钉钉或 QQ。软件检查云端绑定地址是否可用。如果可用，生成二维码、绑定码和过期时间。扫码成功后，用户可以从手机或聊天平台发送命令，例如“今日状态”或“给 buyer@company.com https://company.com 写开发信”。如果云端绑定地址未配置，页面必须明确显示“需要先配置云端绑定地址，才能生成手机可扫码二维码”，不得生成坏二维码，不得出现 undefined/。

# 5. 信息架构

Hermills 的左侧导航保持固定，最多展示高频业务入口，避免变成复杂后台。

推荐主导航顺序是：今日外联、客户、单封写信、批量写信、销售资产、邮箱、签名 Logo、公司资料、聊天控制。

如果高度不足，聊天控制、系统设置、AI 助手、诊断入口可以放到底部工具区，不要和每日业务入口抢位置。

模块分组如下。

每日工作包括今日外联、客户、单封写信、批量写信。这些页面是用户每天打开 Hermills 的主要原因。基础资料包括销售资产、公司资料、签名 Logo，这些会影响写信质量，但更新频率较低。发送能力包括邮箱和聊天控制，这些页面连接外部工具。系统能力包括 AI 助手、系统设置、诊断日志、自动更新、模型/API Key 和本地服务状态，这些能力应放到底部或系统设置中，不要挤进日常业务主流程。

# 6. 已知本地环境与项目位置

当前已知 Hermills 安装和数据位置如下，具体执行时仍以用户本机实际环境为准。

Hermills 当前安装位置可能是：`D:\hermills\Hermills.exe`。软件数据和配置可能存放在：`C:\Users\Lenovo\AppData\Roaming\hermills`。本地代码仓库可能位于：`C:\Users\Lenovo\Documents\Codex\2026-06-10\xueckes-collab-hermills-https`。

执行 Agent 不得假设这些路径一定存在。执行前必须检查当前仓库的真实结构、`package.json`、前端入口、样式系统、组件目录和构建命令。如果仓库结构与本文件描述不同，必须以实际仓库为准，并在进度日志中说明差异。

# 7. 技术栈判断规则

本规格不强行假设前端具体技术栈。执行 Agent 必须先检查项目根目录、`package.json`、`src`、`app`、`components`、`styles`、`tailwind.config`、`vite.config`、`electron`、`tauri`、`next.config` 等文件，确认真实技术栈。

如果项目使用 React、TypeScript、Tailwind、shadcn/ui、Electron、Vite、Next.js 或其他组合，AI 应尊重现有架构。不得为了 UI 重做随意替换技术栈。不得为了使用某个模板而重写整个项目。不得引入大型 UI 框架或新依赖，除非该依赖已经存在或用户明确批准。

如果现有项目没有完整设计系统，AI 可以在前端安全范围内创建 CSS 变量、基础组件和布局组件。如果现有项目已经有组件系统，AI 应优先改造现有组件，不要创建一套重复组件。

# 8. AI 可以修改的范围

AI 可以修改前端页面、UI 组件、CSS、Tailwind class、样式变量、页面布局、导航结构、业务页面的视觉呈现、空状态、加载状态、错误状态、成功状态、按钮文案、提示文案、前端 mock data、与 UI 状态相关的前端类型、展示层的 fallback、纯前端的演示数据和组件组合。

AI 可以新增或改造下面这些 UI 相关组件：AppShell、Sidebar、Topbar、PageHeader、Card、Button、Input、Textarea、Badge、Alert、Modal、Drawer、Stepper、EmptyState、LoadingState、ErrorState、AIProgressTimeline、QualityScoreCard、EvidenceCard、CustomerListItem、EmailEditor、EmailPreview、UploadDropzone、StatusPill、StickyActionBar。

AI 可以为了展示状态而增加安全 mock 数据，但必须标明 mock 数据只用于 UI 展示，不得伪装成真实后端结果。

AI 可以调整页面路由和导航展示，但必须保持业务功能可访问，不得造成旧页面入口丢失。

---

# 9. AI 禁止修改的范围

AI 不得随意修改认证逻辑、注册登录安全流程、用户真实数据结构、数据库 schema、Supabase 表结构、真实邮箱密码或授权码保存逻辑、API Key 保存逻辑、SMTP 发送核心逻辑、IMAP 收信核心逻辑、支付逻辑、套餐权限判断、生产密钥、`.env` 文件、真实任务队列、远程绑定安全策略、真实后端抓取链路、Hermes 本地服务核心逻辑、Scrapling 抓取核心策略、后台学习系统和真实客户数据迁移逻辑。

AI 不得为了让 UI 运行而硬编码真实密钥、伪造发送成功、跳过安全校验、删除失败处理、吞掉错误、把真实错误改成永远成功、把敏感配置写到前端、把客户真实邮箱写入演示数据、把用户真实公司资料当作 mock 数据扩散到测试文件。

如果 UI 需要某个后端字段但当前没有，AI 应该使用前端 fallback、空状态、loading 状态、mock 状态或 TODO 注释，并在最终报告中说明，而不是硬改后端结构。

# 10. 页面优先级

第一优先级是单封写信、批量写信、客户管理、今日外联、邮箱配置。这些页面决定 Hermills 是否像一个可用的外贸工作台。

第二优先级是公司资料、销售资产、签名 Logo、初始化流程。这些页面决定写信质量和用户第一次使用体验。

第三优先级是聊天控制、系统设置、诊断、AI 助手。这些页面重要，但不应该抢每日工作入口。

如果时间有限，必须先把第一优先级页面做成完整工作流，而不是每个页面只做一点皮肤。

# 11. 全局 UI 判断规则

每个 UI 决策都必须回答以下问题。

这个元素是否帮助用户完成客户开发。普通用户能不能看懂。用户点完以后有没有反馈。失败以后用户知道怎么恢复吗。这个信息现在必须显示吗，还是可以藏到高级设置。这个页面有没有一个清楚的主操作。这个页面是否暴露了用户不需要理解的技术概念。这个页面是否只有一个最强主按钮。AI 输出是否有证据、评分和解释。批量任务是否逐条可见。错误是否有人话原因和下一步。

如果答案不清楚，就应该删、藏、合并、降级、重写或放入高级设置。
